# IVD基础

IVD领域相关基础知识整理。

## 1. 质控

在 IVD（体外诊断）设备里，**质控数据（QC）收到之后，并不是简单地判断“QC 值是否在范围内”**。比较标准的做法是：

> **QC结果 → 质控品/项目有效性检查 → 计算统计量 → 单规则判断 → 多规则 Westgard 判断 → 在控/失控 → 失控原因分类 → 对患者结果进行影响评估 → 放行/阻断**

典型流程可以理解成下面这样：
```
质控结果到达
    │
    ▼
┌──────────────────┐
│ QC数据有效性检查   │
│ - 项目是否正确     │
│ - QC批号是否正确   │
│ - 水平是否正确     │
│ - 仪器/试剂状态    │
│ - 数据是否重复     │
└────────┬─────────┘
         ▼
┌──────────────────┐
│ 获取QC统计参数     │
│ Mean / SD / CV   │
│ 或实验室自定义参数  │
└────────┬─────────┘
         ▼
┌──────────────────┐
│ 计算 Z-Score      │
│ Z=(X-Mean)/SD    │
└────────┬─────────┘
         ▼
┌────────────────────────┐
│ 单次QC规则判断           │
│ 1₂ / 1₃ / 2₂ / R₄s...  │
└──────────┬─────────────┘
           ▼
      ┌────┴────┐
      │         │
     在控      失控
      │         │
      ▼         ▼
  QC通过       QC拒绝
      │         │
      ▼         ▼
患者结果      阻止/标记患者结果
放行          调查失控原因
```

但实际系统里还有一个非常重要的概念：
**QC判断通常不是针对单个结果孤立判断，而是针对一个“质控运行（QC Run）”进行判断。**

### 1.1 首先确定QC的上下文
例如设备收到：
```
项目：GLU
试剂批号：A123
QC批号：Q202601
QC水平：Level 1
结果：5.82 mmol/L
```

系统首先要找到这个 QC 对应的统计参数：
```
Mean = 5.00
SD   = 0.25
```

然后计算：
```
Z = (5.82 - 5.00) / 0.25
  = 3.28
```

也就是：
```
+3.28 SD
```

这时候就已经触发了非常典型的（`1_3s`）：
```
1₃s
```

### 1.2 QC通常至少有两个浓度
IVD设备比较常见的是：
```
Level 1（低值）
Level 2（高值）
```

例如：

| QC      |  Mean |   SD |  当前结果 |
| ------- | ----: | ---: | ----: |
| Level 1 |  5.00 | 0.25 |  5.10 |
| Level 2 | 10.00 | 0.50 | 10.20 |

系统需要分别计算：
```
L1 Z = (5.10 - 5.00) / 0.25 = +0.4
L2 Z = (10.20 - 10.00) / 0.50 = +0.4
```
这两个结果都正常。

因此：
```
QC Run
 ├── Level 1 → Pass
 └── Level 2 → Pass

最终 Run → In Control
```

这里就开始涉及你之前做的**质控审核/智能审核**里面一个很重要的问题：

> **单个 QC 结果的状态 ≠ 整次 QC Run 的状态 ≠ 项目的 QC 状态。**

### 1.3 Westgard规则

**Westgard 不是一个“所有 IVD 设备强制统一采用”的标准**

**Westgard 规则（Westgard multirule）是一套非常经典、广泛使用的临床实验室内部质量控制（IQC）判定规则体系**，主要用于判断 QC 是否出现随机误差或系统误差。

常见规则包括：

- `1₂s`：警告
- `1₃s`：失控
- `2₂s`：失控
- `R₄s`：失控
- `4₁s`：失控
- `10x`：失控

它的核心作用是：

> **利用 QC 结果相对于 Mean/SD 的位置，以及 QC 历史结果之间的关系，判断分析系统是否处于受控状态。**

但不要把它等同于 ISO/CLSI 标准，可以这样理解：

|类型|作用|
|---|---|
|ISO 15189 等|实验室质量管理/能力认可要求|
|CLSI 文件|实验室质量控制等方面的规范/指南|
|**Westgard Rules**|**具体的 QC 统计判定方法/规则体系**|
|Levey-Jennings 图|QC 数据的统计可视化方法|

质控品靶值&标准差：
```
Mean = 100
SD   = 5

±2SD = 90 ~ 110
```

几种常见规则的解释：

|              规则               | 含义                                                           | 质控结果值 | z-score                                                                                                                                                     |        触发方式         | 备注/用途                                                         |
| :---------------------------: | ------------------------------------------------------------ | :---: | ----------------------------------------------------------------------------------------------------------------------------------------------------------- | :-----------------: | ------------------------------------------------------------- |
|            **1₂s**            | 一个 QC 结果超过 ±2SD                                              |  111  | Z = (111 - 100) / 5 = +2.2 SD                                                                                                                               |         报警          | 警告，触发进一步检查，**1₂s通常是警告规则，而不是直接判失控**<br>![](img/01.IVD基础-4.png) |
|            **1₃s**            | 一个 QC 结果超过**同一侧** ±3SD                                       |  116  | Z = +3.2 SD                                                                                                                                                 |         失控          | 检测较大的误差<br>![](img/01.IVD基础-5.png)                            |
|            **2₂s**            | 连续两个 QC 结果超过**同一侧** ±2SD                                     |   /   | Z1 = +2.3 SD<br>Z2 = +2.5 SD                                                                                                                                |         失控          | 检测系统误差<br>![](img/01.IVD基础-2.png)                             |

|          **2of3₂s**           | 在连续三个相关的质控观测值中，至少两个超过均值**同一侧**的 ±2SD 限值                      |       | Z1 = +2.1 SD<br>Z2 = +0.1 SD<br>Z3 = +2.5 SD                                                                                                                |         失控          | 检测系统误差<br>![](img/01.IVD基础-7.png)                             |

**关键是“同一批次/同一次运行”**
R₄s 特殊说明：
假设：
```
Run 1:
  L1 = +2.1
  L2 = -0.5

Run 2:
  L1 = +0.8
  L2 = -2.3
```
不能拿：
```
Run 1 L1 = +2.1
Run 2 L2 = -2.3
```
然后说：
```
差值 = 4.4 SD → R_4s
```
这种判断通常是不成立的。

### 1.4 什么时候应该使用多规则QC程序？

> 有时，一个单一的规则QC过程可以为您提供所需的所有错误检测，同时保持较低的错误拒绝。这通常意味着消除 $1_{2s}$ 规则，因为它的高错误拒绝，并考虑其他规则，如 $1_{2.5s}$，$1_{3s}$ 和$1_{3.5s}$，它们具有可接受的低错误拒绝率。剩下的问题是这些其他单规则QC程序是否可以提供足够的错误检测。如果医学上重要的错误可以在90%的时间内被检测到（即，错误检测概率为0.90或更高），则单个规则QC程序就足够了。如果单规则QC程序不能提供90%的错误检测，则应考虑多规则QC程序。一般来说，您会发现单规则QC程序适用于高度自动化和非常精确的化学和血液分析仪，但您应避免使用2s控制限或 $1_{2s}$ 控制规则，以最大限度地减少浪费并降低成本。早期的自动化系统和手动方法通常会受益于多规则QC程序的改进错误检测。

> 为了准确地确定何时使用单规则或多规则QC程序，您需要定义每个测试所需的质量，查看您的方法所达到的精密度和准确度，然后评估不同候选QC程序的错误拒绝（$P_{fr}$）和错误检测（$P_{ed}$）的概率。目标是90%的错误检测（$P_{ed}$为0.90或更高）和5%或更低的错误拒绝（$P_{fr}$ 为0.05或更低）。对于很少出现问题的非常稳定的分析系统，您可以满足于较低的错误检测，比如50%。(See[QC -](https://www.westgard.com/lessons/quality-management/lesson3.html "QC - The Planning Process")选择适当的单规则和多规则QC程序的实用方法的规划过程。）

## 3. ASTM & HL7

### 3.1 ASTM
#### 3.1.1 ASTM是什么？

ASTM 最常见的是指基于 **ASTM E1381 / E1394** 的实验室仪器通信标准。

在 IVD 场景中，经常看到：
```
仪器  <---- ASTM ---->  LIS / 中间件
```

例如：
```
 血球仪
   │
   │ ASTM
   ▼
中间件 / LIS
   │
   ▼
  HIS
```

ASTM 的特点是：
- 面向实验室仪器
- 协议比较轻量
- 通信通常基于 TCP/IP 或串口
- 数据采用**记录（Record）+ 字段（Field）**结构
- 有明确的 ACK / NAK / ENQ / EOT 等通信控制
- 很多老牌 IVD 仪器仍然大量使用

#### 3.1.2 ASTM 数据长什么样？

ASTM 的一个核心特点是**分层结构**：
```
Message
 ├── Header
 ├── Patient
 ├── Order
 ├── Result
 └── Terminator
```

例如可以简化理解成：
```
H|...
P|...
O|...
R|...
L|...
```

其中：

| Record | 含义                       |
| ------ | ------------------------ |
| H      | Header                   |
| P      | Patient                  |
| O      | Order                    |
| R      | Result                   |
| C      | Comment                  |
| M      | Manufacturer Information |
| L      | Terminator               |

示例：
```
H|\^&|||Analyzer||||||||||P
P|1||PAT001||Zhang^San
O|1|SAMPLE001||^^^GLU
R|1|^^^GLU|5.6|mmol/L|...
L|1|N
```

#### 3.1.3 ASTM 的真正难点：不只是这些文本

典型通信过程：
```
Sender                         Receiver

   ENQ  ------------------------>
        <------------------------ ACK

   STX + data + ETX + checksum ->
        <------------------------ ACK

   EOT  ------------------------>
```

其中：
```
ENQ = Enquiry
ACK = Acknowledge
NAK = Negative Acknowledge
STX = Start of Text
ETX = End of Text
EOT = End of Transmission
```

通信模型：
```
┌───────────────────────────┐
│       ASTM Message        │
│                           │
│ H / P / O / R / L         │
└─────────────▲─────────────┘
              │
┌─────────────┴─────────────┐
│     ASTM Communication    │
│                           │
│ ENQ / ACK / NAK / EOT     │
│ STX / ETX / checksum      │
└─────────────▲─────────────┘
              │
┌─────────────┴─────────────┐
│ TCP / Serial / RS232      │
└───────────────────────────┘
```

#### 3.1.4 协议字段


### 3.2 HL7

#### 3.2.1 HL7是什么？

HL7 的全称是：**Health Level Seven**

它主要解决的是**医疗信息系统之间的数据交换**。

例如：
```
HIS
 │
 ├──── HL7 ──── LIS
 │
 ├──── HL7 ──── EMR
 │
 └──── HL7 ──── RIS
 
 LIS
 │
 └──── HL7 ──── IVD Middleware
                         │
                         └── Analyzer
```

HL7 的范围比 ASTM 大得多。

它不仅描述检验结果，还可以描述：

- 患者信息
- 就诊信息
- 医嘱
- 检验申请
- 检验结果
- 诊断
- 用药
- ADT
- 费用
- 医疗文档等

#### 3.2.2 HL7 的结构

医院里面传统 HL7 最常见的是：**HL7 v2.x**

HL7 v2 的消息也是文本形式。

例如：
```
MSH|^~\&|LIS|LAB|HIS|HOSPITAL|202610130900||ORU^R01|123456|P|2.5.1
PID|1||123456^^^HOSPITAL||Zhang^San
OBR|1||S001|GLU^Glucose
OBX|1|NM|GLU^Glucose||5.6|mmol/L|...
```

消息结构：
```
Message
   │
   ├── Segment
   │      │
   │      ├── Field
   │      │      ├── Component
   │      │      │      └── Subcomponent
   │      │      │
   │      │      └── ...
   │      │
   └── ...
```

#### 3.2.3 HL7 还有一个很重要的东西：MLLP

HL7 v2 本身是消息格式，而实际 TCP 传输通常使用：

**MLLP（Minimal Lower Layer Protocol）**

大概是：
```
<SB>
   HL7 message
<EB>
<CR>
```

也就是：
```
VT
MSH|^~\&|...
PID|...
OBR|...
OBX|...
FS
CR
```

通常可以理解成：
```
TCP
 ↓
MLLP Frame
 ↓
HL7 Message
 ↓
HL7 Segment Parser
```

因此不要把：`HL7=TCP协议` 简单等同起来。

更准确的是：
```
HL7 v2
   ↓
消息格式

MLLP
   ↓
HL7 在 TCP 上的常见传输封装
```

#### 3.2.4 消息类型（事件）

HL7 v2 的消息头 `MSH-9` 并不是简单的一个字符串，而是一个组合字段：
```
MSH-9 = Message Type ^ Trigger Event ^ Message Structure
```

`ORU^R01`、`OML^O21` 这些严格来说不是“协议”，而是 **HL7 v2 Message Type + Trigger Event（消息类型 + 触发事件）**。

最常见的消息类型：

| 消息        | 主要用途          | IVD/LIS 重要性 |
| --------- | ------------- | ----------- |
| `ORM^O01` | 通用医嘱/订单       | ⭐⭐⭐         |
| `OML^O21` | 实验室订单         | ⭐⭐⭐⭐⭐       |
| `OML^O33` | 实验室订单         | ⭐⭐⭐⭐        |
| `ORU^R01` | 观察/检验结果       | ⭐⭐⭐⭐⭐       |
| `ORU^R30` | 批量/特定结果查询响应场景 | ⭐⭐          |
| `OUL^R21` | 上报实验室检验结果     |             |
| `ACK`     | 通用确认          | ⭐⭐⭐⭐⭐       |
| `QRY^Q01` | 查询            | ⭐⭐⭐         |
| `QBP`     | 查询参数          | ⭐⭐⭐⭐        |
| `RSP`     | 查询响应          | ⭐⭐⭐⭐        |

#### 3.2.5 协议字段

### 3.3 ASTM vs HL7

简单对比：

| 对比维度   | ASTM        | HL7                 |
| ------ | ----------- | ------------------- |
| 主要领域   | 实验室仪器       | 整个医疗信息系统            |
| 常见场景   | 仪器 ↔ LIS    | HIS/LIS/EMR/RIS/仪器  |
| 典型版本   | E1381/E1394 | HL7 v2.x            |
| 数据结构   | Record      | Segment             |
| 典型记录   | H/P/O/R/L   | MSH/PID/ORC/OBR/OBX |
| 底层通信   | TCP/串口      | TCP/MLLP 等          |
| 复杂程度   | 相对简单        | 更复杂                 |
| IVD 仪器 | 非常常见        | 也很常见                |
| 医院信息系统 | 较少          | 非常常见                |
| 历史设备   | 很多          | 很多                  |

它们的数据结构其实很像：

ASTM：
```
H
P
O
R
L
```

HL7:
```
MSH
PID
ORC
OBR
OBX
```

本质上都是：
```
一条 Message
    ↓
多个 Record / Segment
    ↓
多个 Field
    ↓
结构化数据
```

所以从软件架构上，完全可以抽象成：
```
                ┌───────────────┐
                │ Domain Model  │
                │               │
                │ Patient       │
                │ Order         │
                │ Result        │
                └───────▲───────┘
                        │
              ┌─────────┴─────────┐
              │                   │
         ASTM Adapter         HL7 Adapter
              │                   │
         ASTM Parser          HL7 Parser
              │                   │
          TCP/Serial           MLLP/TCP
```

最终统一成：
```
struct Patient
{
    std::string id;
    std::string name;
};

struct Order
{
    std::string sampleId;
    std::string testCode;
};

struct Result
{
    std::string testCode;
    std::string value;
    std::string unit;
};
```

然后：
```
ASTM
   ↓
ASTM Parser
   ↓
Patient / Order / Result

HL7
   ↓
HL7 Parser
   ↓
Patient / Order / Result
```

这样你的业务层完全不需要关心到底是 ASTM 还是 HL7。

典型的中间件架构（agent）：
```
                    LIS
                     │
                 HL7 / ASTM
                     │
               ┌─────▼─────┐
               │ Middleware│
               │   Agent   │
               └─────┬─────┘
                     │
          ┌──────────┼──────────┐
          │          │          │
        ASTM       TCP/IP      Serial
          │          │          │
       仪器 A      仪器 B      仪器 C
```
