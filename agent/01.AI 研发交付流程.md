# AI 研发交付流程

本文基于项目已有的 AI 应用报告整理，目标是把"需求指定、文档生成、任务开发、合并、MR、审核、评论修复、流水线部署"串成一条可复用的工程闭环。

前提：需求已录入禅道，采用 [zentao-cli](https://www.npmjs.com/package/zentao-cli) 打通禅道系统


## 需求到文档

Qoder/Codex 负责拿到需求 ID，并把需求上下文交给 [OpenSpec](https://github.com/Fission-AI/OpenSpec)。OpenSpec 不直接写业务代码，而是生成可评审、可拆解、可追踪的开发文档。
扩展阅读：[其他SDD：spec-kit](https://github.com/github/spec-kit)

**Default quick path (core profile):**

```
/opsx:explore ──► /opsx:propose ──► /opsx:apply ──► /opsx:sync ──► /opsx:archive
   (optional)
```
**Expanded path (custom workflow selection):**

```
/opsx:new ──► /opsx:ff or /opsx:continue ──► /opsx:apply ──► /opsx:verify ──► /opsx:archive
```

```mermaid
sequenceDiagram
    actor 用户
    participant Qoder
    participant 禅道
    participant OpenSpec
    participant Docs as OpenSpec 文档

    用户->>Qoder: 输入需求 ID
    Qoder->>禅道: 查询需求详情
    禅道-->>Qoder: 返回背景 / 范围 / 验收标准
    Qoder->>OpenSpec: 接管需求上下文
    OpenSpec->>Docs: 生成 spec.md
    OpenSpec->>Docs: 生成 design.md
    OpenSpec->>Docs: 生成 tasks.md
    Docs-->>用户: 输出可评审文档

    alt 需求信息不完整
        用户->>Qoder: 补充业务规则 / 边界条件
        Qoder->>OpenSpec: 更新文档
    else 文档通过评审
        用户->>Qoder: 确认进入开发
    end
```

## `tasks.md` 到开发实现

[Superpowers](https://github.com/obra/superpowers) 接管 OpenSpec 产出的 `tasks.md` 后，按任务粒度推进开发。复杂任务先拆分，涉及缺陷时使用系统化调试，涉及实现时按任务完成代码、验证和自审。

```mermaid
sequenceDiagram
    actor 用户
    participant Superpowers
    participant Tasks as tasks.md
    participant Code as 项目代码
    participant Verify as 本地验证
    participant GitLab

    用户->>Superpowers: 接管 tasks.md
    Superpowers->>Tasks: 读取任务列表和验收标准

    loop 每个任务
        Superpowers->>Code: 修改代码
        Superpowers->>Verify: 运行相关验证
        Verify-->>Superpowers: 返回验证结果

        alt 验证失败
            Superpowers->>Code: 定位原因并修复
        else 验证通过
            Superpowers->>Tasks: 标记任务完成
        end
    end

    用户->>Superpowers: 用户确认
    Superpowers->>GitLab: commit / push
```



### Superpower完整流程

Superpowers 是一个**纯 Skill 驱动的开发工作流插件**，核心价值在于：

1. **强制纪律**：通过 Iron Law + Red Flags 机制防止跳过设计、跳过测试、跳过验证
2. **完整工作流**：从头脑风暴→设计→计划→TDD 实现→代码审查→验证完成，覆盖开发生命周期
3. **子 Agent 协作**：通过分派隔离上下文的子 Agent 实现高质量并行开发和两阶段审查

## 同步 `dev` 与创建 MR

`sync-dev` 用于在创建 MR 前同步目标分支代码，降低 MR 阶段的冲突和流水线失败概率。`create-mr` 负责把本地分支转换成可审核的 GitLab MR。

```mermaid
sequenceDiagram
    actor 用户
    participant Qoder
    participant Local as 本地分支
    participant GitLab
    participant Dev as dev 分支
    participant MR as Merge Request

    用户->>Qoder: 执行 sync-dev
    Qoder->>GitLab: 拉取最新 dev
    GitLab-->>Qoder: 返回 dev 更新
    Qoder->>Local: 合并 dev

    alt 存在冲突
        Qoder->>Local: 辅助解决冲突
        用户->>Local: 确认冲突处理结果
    else 无冲突
        Qoder->>Local: 保持分支可合并
    end

    用户->>Qoder: 执行 create-mr
    Qoder->>GitLab: 推送分支
    Qoder->>MR: 创建标题 / 描述 / 变更摘要
    MR-->>用户: 返回 MR 链接
```



## 代码审核与评论修复

`codeView` 负责对 MR 进行代码审核，重点识别阻断合并的问题。`resolve-mr-comments` 负责读取 MR 评论，按评论修复代码并补充提交，形成审核闭环。

```mermaid
sequenceDiagram
    actor 用户
    participant GitLab
    participant CodeView
    participant Qoder
    participant Code as 项目代码

    GitLab->>CodeView: MR 创建或更新
    CodeView->>GitLab: 读取 diff / commit / MR 描述
    CodeView->>CodeView: 执行代码审核
    CodeView-->>用户: 输出阻断项 / 风险项 / 建议项

    alt 存在阻断评论
        用户->>Qoder: 执行 resolve-mr-comments
        Qoder->>GitLab: 读取 MR 评论
        Qoder->>Code: 修复问题
        Qoder->>GitLab: push 补充提交
        GitLab->>CodeView: 重新触发审核
    else 审核通过
        用户->>GitLab: 准备合并
    end
```



## 流水线部署项目

MR 审核通过后进入合并和流水线部署。部署阶段关注流水线状态、部署环境、验证结果和失败回滚路径。

```mermaid
sequenceDiagram
    actor 用户
    participant GitLab
    participant Pipeline as GitLab Pipeline
    participant Build as 构建任务
    participant Deploy as 部署任务
    participant Env as 目标环境

    用户->>GitLab: 合并 MR
    GitLab->>Pipeline: 触发流水线
    Pipeline->>Build: 安装依赖并构建
    Build-->>Pipeline: 构建结果

    alt 构建失败
        Pipeline-->>用户: 返回失败日志
    else 构建成功
        Pipeline->>Deploy: 分环境执行部署(dev/test)
        Deploy->>Env: 发布到目标环境
        Env-->>用户: 钉钉通知部署状态
    end
```



## 流程总览

| 阶段 | 入口 | 产物 |
| --- | --- | --- |
| 需求指定 | 在 Qoder 中指定需求 ID | 明确的需求上下文 |
| 文档生成 | OpenSpec 接管需求 | `spec.md`、`design.md`、`tasks.md` |
| 任务开发 | Superpowers 接管 `tasks.md` | 代码修改、验证记录 |
| 同步开发分支 | `sync-dev` | 已合并最新 `dev` 的工作分支 |
| 创建 MR | `create-mr` | GitLab Merge Request |
| 代码审核 | `codeView` | 审核报告、阻断项、建议项 |
| 评论修复 | `resolve-mr-comments` | 已处理的 MR 评论与补充提交 |
| 流水线部署 | GitLab Pipeline | 可验证的部署结果 |


```mermaid
sequenceDiagram
    actor 用户
    participant Qoder
    participant OpenSpec
    participant Superpowers
    participant Code as 项目代码
    participant GitLab
    participant CodeView
    participant Pipeline as GitLab Pipeline

    用户->>Qoder: 指定需求 ID
    Qoder->>OpenSpec: 澄清需求上下文
    OpenSpec-->>Qoder: 生成 spec / design / tasks
    Qoder->>Superpowers: 提交 tasks.md
    Superpowers->>Code: 按任务开发与验证
    用户->>Qoder: 执行 sync-dev
    Qoder->>GitLab: 同步 dev 并解决冲突
    用户->>Qoder: 执行 create-mr
    Qoder->>GitLab: 创建 MR
    GitLab->>CodeView: 触发代码审核
    CodeView-->>用户: 输出审核报告
    用户->>Qoder: 执行 resolve-mr-comments
    Qoder->>GitLab: 修复评论并推送补充提交
    GitLab->>Pipeline: 触发流水线
    Pipeline-->>用户: 返回部署结果
```



## 建议

1. 需求类开发优先从需求 ID 进入，避免只靠口头描述生成代码，导致以后也不知道当时怎么描述的问题
2. OpenSpec 阶段先评审文档，再进入编码，减少需求边界不清导致的返工。
3. Superpowers 阶段围绕 `tasks.md` 推进，避免跳过验证和自审。
4. MR 前先执行 `sync-dev`，让冲突尽早暴露在本地。
5. MR 后使用 `codeView` 和 `resolve-mr-comments` 形成"审核-修复-复审"的闭环。



## 遇到的问题

#### 1. Skill 触发不可控（随机性）

- 多个 Skill 同时存在时，触发哪个 Skill 是不确定的，比如superpowers有很多skill，没有看到做TDD和subagent操作
- 缺乏明确的触发优先级机制

#### 2. Skill 边界不清晰（功能重叠）

- `openspec` 和 `Superpower` 都涉及需求讨论，职责划分模糊
- 目前写了一个Skill来衔接openspec和superpowers，还在测试阶段

#### 3. 开发粒度讨论？

- 当前直接对需求进行开发，前端和后端都是同一个需求描述，但又是要实现两套不同的代码，是否需要开发人员去拆解更细的task
- 是否需要 **需求 → Task 拆解 → 单 Task 开发** 的流水线机制



## 后续计划：Agent 工程化能力演进

后续建设重点从"单次 AI 辅助编码"升级为"可观测、可编排、可复用的 Agent 任务开发体系"。

核心演进方向可以概括为四个关键词：`prompt`、`context`、`harness`、`loop`。

| 能力 | 作用 |
| --- | --- |
| `prompt` | 没把话说清楚，模型就乱猜。解决"怎么说"。 |
| `context` | 话说清楚了，但模型不知道我们的业务背景信息。解决"给什么"。 |
| `harness` | 说清楚了信息也够了，但 Agent 跑长任务还是会偏。解决"谁来兜底"——把每次犯错就把修复沉淀进环境，让它结构上不可能再犯同样的错。 |
| `loop` | 我们需要按回车，解决"让它自己循环转"，执行交给 Agent，人去设计环境和判断结果 |
